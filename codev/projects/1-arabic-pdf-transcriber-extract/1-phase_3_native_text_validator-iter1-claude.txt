### Issues Found

**1. `page: Any` type annotation (COMMENT)**

Plan says `validate_page(page: NativePage) -> ValidationResult`. Implementation uses `page: Any` with `getattr()` duck-typing. Avoids circular import (validate → extract), which is reasonable. But CLAUDE.md says "NEVER use `any`/`Any`." Could use `TYPE_CHECKING` guard or a Protocol:

```python
from __future__ import annotations
from typing import TYPE_CHECKING
if TYPE_CHECKING:
    from arabic_pdf_transcribe.extract.native import NativePage
```

or define a small `ValidatablePage` Protocol in this module. Not blocking — works correctly — but worth fixing for type safety.

**2. LICENSES.md missing entries for `digital-broken/` fixtures (COMMENT)**

Plan deliverable says "license documented" for the two new broken fixtures. `LICENSES.md` table has no rows for `digital-broken/mojibake.pdf` or `digital-broken/replacement-glyphs.pdf`. They're project-generated via `tools/generate_fixtures.py` (MIT), same as the digital-clean fixtures — just needs rows added.

**3. Mojibake fixture uses `?` (U+003F), not actual mojibake codepoints (COMMENT)**

The "mojibake" fixture contains ASCII `?` characters — not private-use or misencoded Arabic codepoints that real mojibake produces. It renders as question marks visually and textually. This means:
- Replacement-glyph signal won't catch it (no PUA/FFFD)
- Arabic-ratio signal won't catch it (no Arabic present, so `has_arabic=False` → exempted)
- Only word-boundary KL catches it (short single-char tokens diverge from reference)

It works for tests because the KL signal rejects it, but it's not a realistic mojibake scenario (real broken text layers produce PUA codepoints or Latin-range misencoding, not `?`). Spec test scenario 5 says "digital PDF with mojibake / non-Unicode glyphs → validator rejects it." Current fixture exercises only one signal path. Phase 9 corpus expansion will fix this, so not blocking.
